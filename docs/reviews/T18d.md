## Review

The findings are:

1. **`functions/_lib/fallback/questions.ts:221`, should-fix.** The per-feature ancestor lookups start only after the candidate disease annotations have returned, so they run in series. On a cold cache, annotations 3 s, plus hpoTerm 2 s, plus a 300 ms retry, exceeds the 5 s budget that contract §7.5 gives next-questions. Fix: give this batch of lookups an overall cap of the remaining budget; on timeout, skip the hierarchy filter and return the original order.
2. **`questions.ts:61-64`, should-fix.** In the worst case, 20 patient-side lookups, 15 feature-side lookups, plus 5 candidates × (ORPHA + OMIM annotations + xref) bring the subrequest count close to the Workers free plan limit of 50 per request. Past the limit the annotation calls fail too, so a failure is not just "falling back to the old behaviour"; it breaks the existing feature. Fix: first confirm the real number of xref and annotation calls, then lower the caps, or look up only the patient side on a cold cache.
3. **`questions.ts:238-239`, should-fix.** Ancestors of excluded terms are filtered too, which is wrong logically: the patient not having Headache does not mean the patient lacks its ancestor, a Pain-type feature, so a valid discriminating question is removed (R5.2). An excluded term should filter only its descendants.
4. **`questions.ts:241-243`, nit.** Descendants (more specific terms) of an observed term are removed too. For example, with Jaundice already present, Prolonged neonatal jaundice is removed, and such questions often discriminate between candidates. This matches the task description, but say in a code comment that it is a deliberate trade-off.
5. **`questions.ts:179`, nit.** When `annotated.length < 2` returns early, the requests in `patientAncestors` have already been sent and their results are thrown away, wasting subrequests. Start them only after confirming that at least 2 candidates have annotation data.
6. **Positive conclusion:** the change touches only the 2 claimed files. P9 still holds, because the filter only removes questions and does not change `discriminates`. A failed lookup, a 404 or a malformed response returns `null` and the question is kept, which matches "degrade to the old behaviour". The change does not touch the UI, so the safety wording and data sources of design.md §7 are not affected.
7. **Missing tests, should-fix.** No tests cover these cases: with a mocked ancestor endpoint failing, the output is the same as before the change; ancestor and descendant filtering is correct; the order is stable.
