1. **`functions/api/extract.ts:20`, should-fix.** This imports Jerry's internal module `engine/hpo` directly to get `HPO_VERSION`, bypassing the public entry point `engine/index.ts` that contract §6 prescribes. If Jerry later changes the internal structure, this will break, and he will not know anyone depends on it. Fix: ask Jerry to export this constant from `engine/index.ts`, or to include `dataVersions` in what `getDemoCase` returns, then import from index.

2. **`functions/api/extract.ts:224`, nit.** `dataVersions.hpo` in the demo response is always `"unknown"`. Contract §9 requires recorded data to keep the original `dataVersions`, and the §7.2 example shows `"2025-11-24"`. Under open question 6, `"unknown"` is allowed, but then the HPO attribution in the brief and the footer (R8.1) will show "version unknown". Fix: once open question 6 is settled, have the demo data carry the real version number.

3. **`functions/api/extract.ts:120`, should-fix.** Contract §7.2 sets a total grounding budget of 4 seconds, but there is no overall deadline here. If the id lookup fails and the engine's `byLabel` tries several search variants in turn, at 2 seconds each plus one retry, the total time will exceed 4 seconds. Fix: put an overall deadline on `groundTerms` at the function level, treat a timeout as 504 and use the demo fallback; or ask Jerry to implement this budget in the engine.

4. **`functions/_lib/respond.ts:91`, nit.** The message `InvalidInput` returns is "The request has an invalid field: q.", which does not tell the user what to do. Contract §4 requires the message to say what the user can do. Fix: give an actionable hint per field, for example that q needs 2 to 100 characters.

5. **`functions/api/health.ts:26`, nit.** After changing from `onRequestGet` to `onRequest`, HEAD requests now return 405. If any monitor probes with HEAD, it will wrongly report the site as down. Fix: allow HEAD, or confirm that no monitor uses HEAD.
